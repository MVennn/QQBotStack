# 版本规则

> **一句话**：版本晋升规则（**正本**）：三段式进位、怎么判有没有功能更新、
> 版本号只在 CHANGELOG 维护、不发版就不动号。

---

## 1. 三段式进位

版本号形如 `vX.Y.Z`（`v` 前缀只属于 **git tag**，文档与文件名不带）。

| 变更性质 | 进位 |
|---|---|
| 有功能更新（脚本新增、阶段新增、默认行为变更） | **次版本 +0.1.0**，补丁位归零 |
| 只有缺陷修复 / 文档修正 | **补丁版本 +0.0.1** |
| 破坏性变更（目录结构变动、参数改名、默认端口变更） | 次版本 +0.1.0，并在 CHANGELOG 单列「不兼容」 |

## 2. 怎么判「有没有功能更新」

口诀：**使用者拿到的「能做什么」有没有变？**

| 变更 | 算功能更新吗 |
|---|---|
| 新增一个部署阶段或一个参数 | ✅ 算 |
| 换上游组件大版本（如 AstrBot 4→5） | ✅ 算，且要重跑验收 |
| 改默认端口或目录约定 | ✅ 算（且属破坏性） |
| 修一个判定错误 | ❌ 不算 |
| 改文档措辞、补索引 | ❌ 不算 |

## 3. 版本号在哪维护

**只在根 `CHANGELOG.md` 的段标题里**（`## [0.1.0] — YYYY-MM-DD`）。
本仓没有 `package.json` / `VERSION` 文件，不要新建第二个版本号载体。

`docs/release-notes/<版本>.md` 的文件名与版本号一致，**不带 `v`**。

## 4. 发版步骤

1. 把 CHANGELOG 顶部的 `## [未发布]` 改成 `## [X.Y.Z] — YYYY-MM-DD`
2. 新建 `docs/release-notes/X.Y.Z.md`（格式正本：[release-notes/README.md](release-notes/README.md)）
3. `git tag vX.Y.Z && git push origin vX.Y.Z`
4. `gh release create vX.Y.Z --notes-file docs/release-notes/X.Y.Z.md`

## 5. 不发版的时候：不要动版本号

**没有要发的东西，就不要改 CHANGELOG 里的版本段标题，也不要打 tag。**
日常改动一律追加在 `## [未发布]` 下面。

判断标准：**这次改动需要别人重新部署才能用上吗？** 不需要就别动号。
