# release-notes/

> **一句话**：面向使用者的 Release 说明模板与写法 —— 文件名 = 版本号（不带 `v`），
> 首行加粗总结、次行反馈入口、清单式正文、固定风险尾巴。

放**面向使用者**的 Release 说明，**文件名 = 版本号本身**（如 `0.1.0`），**不带 `v` 前缀** ——
`v` 前缀只属于发版 tag。版本号与 [CHANGELOG.md](../../CHANGELOG.md) 的段标题一致。

## 为什么要单独放一份

`CHANGELOG.md` 是**开发者记录**：症状 / 根因 / 改法 / 验证结果 / 踩坑。
Release 说明是**给使用者看的**，要短、写成清单、只讲「我现在能拿到什么」。

本仓的「使用者」是**要自己搭一套 QQ bot 的人** —— 他关心的是：
「跑哪条命令能装好、哪几步必须我亲自做、出问题了查哪」。

## 形状

**清单，不是文章。** 开头一句加粗概述，`## 本版内容` 下按分区一行一条，最后是固定尾巴。
**第一行必须是加粗总结；紧接的那一行是反馈入口**（一行，链接用绝对地址），
然后才是 `## 本版内容`。

```markdown
**首版：把「QQ bot + 协议端 + 模型网关」装成一套，从零到能对话只要一条命令。**

遇到问题、想要新功能，到 [Issues](https://github.com/MVennn/QQBotStack/issues/new/choose) 反馈 —— 请附 Windows 版本、出问题的组件、执行的完整命令与输出原文。

## 本版内容

**脚本**

- 新增 tools/deploy-stack.ps1 —— 分阶段幂等部署，网关阶段不需要人工。
- 新增 tools/verify-stack.py —— 五步验收，失败项直接给排错条目号。

**文档**

- 新增 部署设计 —— 三块组件的版本与许可核实、方案取舍、风险与回退。
- 新增 排错手册 —— 八个高频现象，各配可直接粘贴的排查命令。

---

需要 Windows 10/11、一个 QQ 号（建议小号）、一个 WorkBuddy 账号。
部署脚本会装 QQ 与 AstrBot、建计划任务，执行前请先看 [架构与边界](../ARCHITECTURE.md) 的「会改什么」。

---

> 风险提示：QQ 协议端登录有账号风险，请使用小号；同一批 WorkBuddy 账号不要在两台机器同时跑。
> 详见 [凭据与账号配置](../SECRETS.md) 与 [安全策略](../../SECURITY.md)。
```

结尾那两行是**固定尾巴**，每版照抄不动，**不算重复内容**。

## 反馈入口：写在开头，链接必须是绝对地址

每份说明的**第二行**放一行反馈入口，不是清单条目：

- 链接写绝对地址 `https://github.com/MVennn/QQBotStack/issues/new/choose`
  —— 说明会被贴到 Release 页面，相对链接在那里解析不到；
- 已发布的历史正文**不回填**；这条规则只对**新版本**生效。

### 一条怎么写

```text
新增 / 调整 / 修复 / 优化 + 对象名 —— 入口或位置；一句话你拿到什么
```

- **动词只有四个**：新增、调整、修复（含底层与实现层）、优化；另有「移除」。
- **对象名照抄仓库里的实物**（文件名 / 文档名 / 脚本名）。
- **入口**写你找得到的位置：「仓库根 README」「docs/ 索引」；不需要找入口的写场景（「目标机上」）。
- **一句话说完你拿到什么**。不写怎么用、不写为什么。
- 一行一条。

## 覆盖率红线

**凡本版改过的东西，必须全部出现在 Release 说明里**，一行一条。没有例外。
写完拿 CHANGELOG 对应段落逐条对。

## 别写这些

| 别写 | 为什么 |
|---|---|
| 第二人称操作步骤 | 步骤归 README 与排错手册 |
| 原因与取舍 | 解释属于 CHANGELOG |
| 实现原理、脚本内部机制 | 同上 |
| 「本版没有破坏性变更」 | 没变更就不用声明；**有**的时候才必须写 |

> 本仓当前**未接入自动发布流水线**。
> 发版 = 打 tag + 手工把 `docs/release-notes/<版本>.md` 贴进 Release 页面。
